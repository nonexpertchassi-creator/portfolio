01 / SYSTEM

PUI-X — 사내 프로덕트 시스템

역할 기획 · 설계 · 구현 · 배포 · 운영 범위 단독 형태 카카오톡 채널 카드뷰 렌더러
Problem definition

동일 템플릿 40종을 수작업으로 제작·유지하던 구조였습니다. 1px 단위 수정 요청 하나가 40회의 반복 작업과 40회의 오류 가능성으로 확산됐고, 그 과정에서 발생하는 커뮤니케이션 비용이 실제 제작 시간을 넘어섰습니다.

문제를 작업량이 아니라 “수정 비용이 산출물 개수에 비례하는 구조”로 정의하고, 비례 관계 자체를 끊는 방향으로 시스템을 설계했습니다.

커뮤니케이션 비용의 실체는 요청 전달 경로였습니다. 수정 요청이 작업 파일과 검수본 사이를 오갈 때마다 40종의 반영 여부를 다시 확인해야 했습니다.

Operational proof

운영 증거 — 수치보다 상태

  • IN USE2026년 배포 후 팀 운영에 사용 중
  • REPLACED카카오 커머스 카드 40종의 수작업 제작·렌더·캡처 업무를 대체
  • TRANSFERRED최초 제작자가 직접 관리하지 않는 현재도 운영 중
Decision log

비례 비용을 끊은 세 가지 선택

  1. 40개 완성본을 각각 유지 → 수정 전파와 누락 검수가 그대로 40배 → 하나의 템플릿 + variant schema 선택

  2. 사용자 브라우저에서 수동 캡처 → 폰트·해상도·실행 환경에 따라 결과가 달라짐 → 서버 Playwright 일괄 렌더링 선택

  3. 외부 편집기에서 이미지 전처리 → 파일 왕복과 작업자 의존성이 남음 → 배경 제거 + sharp 후처리 파이프라인 선택

02 / BRIDGE

프론트엔드 구조 설계 · 리뷰

PUI-X를 만들 수 있었던 이유이자, SEO/GEO에서 화면과 정보 구조를 함께 다룰 수 있는 근거입니다. 퍼블리싱 실무에서 시작해 팀원의 구조를 리뷰하고 변경 영향도를 문서화하는 역할로 확장했습니다.

HANMAC · STRUCTURE REVIEW

공통 클래스 68개를 영향도 지도로 바꿨습니다

톤앤매너 개편 전에 공통 클래스를 추출하고 페이지별 의존 관계를 매핑했습니다. BEM·SEO 컨벤션, WBS, 광고주 공유용 리스크를 한 문서에 연결해 “고치면 어디가 깨지는가”를 팀이 함께 보게 했습니다.

CASS CONNECT · 0→1 FRONTEND

페이지가 아니라 서비스 흐름을 퍼블리싱했습니다

영수증 업로드, 스탬프·미션, 응모, 마이페이지, FAQ와 내비게이션까지 사용자 화면 전체를 만들었습니다. 화면 단위보다 상태·검증·공통 CSS 경계를 먼저 잡아 신규 서비스의 뼈대를 세웠습니다.

리뷰 기준은 스타일 취향이 아니라 변경 전파 범위, semantic structure, 상태와 검증, 접근성, 크로스브라우저 영향입니다.

03 / SEARCH

SEO / GEO — 같은 방법론이 어디서 꺾이는가

검색엔진과 답변엔진이 이해할 수 있는 구조를 만든다는 공통점은 같지만, 주류·FMCG와 규제 산업은 “짧고 직접적인 답”을 허용하는 범위가 다릅니다. 두 케이스의 대비가 방법론의 핵심입니다.

케이스 A — ABI

BEER · FMCG
진단
비주얼·캠페인 중심 페이지에 제품 entity, 검색 의도, 사용자의 질문에 답하는 텍스트 층이 있는지 봅니다. semantic HTML, heading, meta·canonical, schema까지 같은 관점에서 확인합니다.
개입
Pure Gold의 What / Why / How + FAQ 구조, 한맥의 질문형 콘텐츠를 AEO 관점으로 재구성하고, OB 기업 사이트에는 Schema.org 구조화 데이터를 적용했습니다.
결과
OB의 구조화 데이터 적용은 기존 프로젝트 이력으로 확인됩니다. Pure Gold·한맥은 정보 구조 사례 후보로만 표기하며, 검색 순위·트래픽·AI 인용 성과는 근거가 없어 쓰지 않습니다.
원칙
브랜드 경험을 걷어내지 않고, 그 아래에 공식 답변 층을 만든다.
구현 경험 + 성과 미기재 사례 후보

케이스 B — DB손해보험

FINANCE · REGULATED
진단
상품 설명이 CTA에 도달하기 전에 대상, 보장 범위, 조건, 제외 사항, 고지와 정보 기준을 오해 없이 구분하는지 봅니다. 답변의 짧음보다 조건의 완전성이 우선입니다.
개입
보험 상품 상세의 정보 구조와 화면을 설계하고 PC·모바일 퍼블리싱을 디렉션했습니다. 제품 entity와 핵심 조건, 고지 정보를 순서대로 읽히게 하는 IA를 사용했습니다.
결과
다이렉트DB 상품 페이지의 설계·디자인·퍼블리싱 디렉션 경험은 공개할 수 있습니다. 다만 이를 GEO 노출 성과로 소급해 주장하지 않습니다.
원칙
규제 산업에서는 인용하기 쉬움보다 조건·예외·출처를 잃지 않는 것이 먼저다.
정보 구조 경험 · GEO 성과 미기재
SAME METHOD

질문 → entity → 직접 답 → 근거 → 다음 행동

ABI

짧은 제품 정의와 브랜드 경험을 먼저 연결하고, FAQ로 남은 질문을 닫습니다.

DB

직접 답 뒤에 조건·예외·고지·기준일이 함께 남아야 하며, 이를 줄여서 인용하지 않습니다.

제안서 수십 건에서 뽑은 패턴

클라이언트 정보를 걷어내고 반복된 판단만 남겼습니다. “해봤다”를 넘어서 다음 프로젝트에서도 재현할 수 있는 기준입니다.

PATTERN 01

반복적으로 확인된 진단

브랜드 페이지는 시각 자산은 강하지만, 공식 제품 정의·대상·차이·이용 방법이 독립적으로 인용 가능한 문장으로 남지 않는 경우가 많았습니다.

PATTERN 02

업종별 우선순위의 분기

FMCG는 제품 entity와 경험·FAQ가 먼저이고, 금융은 조건·예외·출처·기준일과 승인된 표현의 경계가 먼저입니다.

PATTERN 03

통과와 무산의 차이

통과 가능성이 높은 제안은 목표 질문, 바꿀 컴포넌트, 공개 가능한 검증 방식을 연결했습니다. “AI 노출 강화”처럼 통제 대상과 증거가 없는 제안은 실행 단위로 내려가지 못했습니다.

Evidence

공개 가능한 증거 설계

BEFORE / AFTER

같은 질문·모델·날짜 조건으로 LLM 답변을 캡처하고, entity 식별·핵심 답·공식 출처 연결만 비교합니다.

OWNED ASSET

PUI-X와 이 포트폴리오에 같은 방법론을 적용해 정보 구조·메타데이터·JSON-LD를 공개 코드로 검증합니다.

PUBLIC SOURCE

포트폴리오 저장소 ↗에서 semantic HTML, canonical과 구조화 데이터를 확인할 수 있습니다.

One-page method

GEO 진단 — 다섯 단계

  1. 01

    Question — 이 페이지가 직접 답해야 할 대표 질문을 한 문장으로 고정

  2. 02

    Entity — 정식 명칭, 운영 주체, 대상, 다른 entity와의 관계를 명시

  3. 03

    Evidence — 출처, 조건, 예외, 기준일을 답과 분리하지 않고 연결

  4. 04

    Structure — heading, 직접 답, 메타·canonical, schema와 내부 링크에 적용

  5. 05

    Verify — 크롤링·스키마·대표 질문을 점검하고 전후 데이터가 있을 때만 성과 표기

04 / CONTROL

AI 협업 방법론 — 언제 믿지 않을 것인가

툴을 나열하지 않습니다. AI가 넓은 컨텍스트에서 그럴듯한 코드를 빠르게 만드는 순간보다, 범위를 좁히고 근거를 요구하며 사람이 승인 경계를 지키는 방식을 문서화합니다.

RULE 01 / CONTEXT

큰 세션을 모듈 단위로 잘랐습니다

9,000줄 규모 세션에서 AI 제안을 그대로 수용하지 않고, 입력·규칙·렌더링·출력 모듈로 컨텍스트를 분리했습니다. 한 번에 해결할 범위를 줄이자 오류가 생긴 경계를 찾기 쉬워졌고 불필요한 토큰 소모도 함께 줄었습니다.

증거 기준 — 한 요청은 한 모듈, 변경 파일과 책임 경계를 먼저 선언

RULE 02 / APPROVAL

AI가 자기 작업을 승인하지 못하게 합니다

탐색 → 구현 → 검증을 분리합니다. 구현을 만든 대화의 설명만 믿지 않고 diff, 영향 범위, 테스트 결과, 되돌리는 방법을 사람이 확인한 뒤 다음 모듈로 넘어갑니다.

중단 조건 — 범위 밖 파일 수정 · 이유 없는 의존성 · 삭제/마이그레이션 · 검증 없는 “완료”

RULE 03 / EVIDENCE

답보다 출처가 남는지를 봅니다

승강기 법령 RAG에서는 추천 질문 345개를 실제로 전수 질의해 답하지 못하는 질문을 걸러냈습니다. 조항 번호·시행일 같은 근거가 빠진 답은 문장이 자연스러워도 통과시키지 않았습니다.

표기 원칙 — AI 페어 결과와 직접 작성 코드를 분리하고, 검증한 범위만 본인 기여로 설명
