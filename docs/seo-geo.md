# SEO / GEO 포트폴리오 노트

> 검색엔진이 페이지를 정확히 수집·해석하고, 사용자가 검색 결과와 답변형 인터페이스에서 필요한 정보를 빠르게 찾도록 만드는 프론트엔드·콘텐츠 설계 기준입니다.

빠르게 적용할 때는 [GEO 진단 방법론 — 1페이지](geo-method.md)의 다섯 단계와 체크리스트를 사용합니다.

## 이 문서의 원칙

- **구현 사실과 성과를 분리합니다.** 코드·문서·배포 화면으로 확인되는 적용 내용만 구현 경험으로 적습니다.
- **검증하지 않은 수치를 만들지 않습니다.** 노출, 순위, 클릭, 전환, AI 답변 인용률은 Search Console·분석 도구·실험 기록이 있을 때만 성과로 표기합니다.
- **SEO와 GEO/AEO를 같은 문제의 연장선으로 봅니다.** 크롤러가 읽는 기술 구조, 사람이 이해하는 정보 구조, 답변엔진이 인용하기 쉬운 명시적 문장을 함께 설계합니다.
- **스키마는 보이지 않는 장식이 아닙니다.** 실제 화면에 있는 브랜드·제품·조직·질문·답변과 일치하는 데이터만 구조화합니다.

## 1. Technical SEO와 semantic HTML

### 문제

화면이 정상적으로 보여도 검색엔진이 같은 내용을 보리라는 보장은 없습니다. 클라이언트 렌더링에만 의존한 본문, 클릭 이벤트로만 이동하는 UI, 중복 URL, 비논리적인 heading 계층은 수집과 해석을 어렵게 만듭니다.

### 전략

1. 핵심 콘텐츠와 링크는 초기 HTML에서 확인할 수 있게 합니다.
2. URL마다 대표 검색 의도와 대표 URL을 하나씩 정합니다.
3. 시각 디자인과 별개로 문서 outline이 독립적으로 이해되게 만듭니다.
4. 키보드·스크린리더 사용성까지 함께 점검합니다. 접근성 좋은 구조는 검색엔진에도 더 명시적인 구조가 됩니다.

### 적용

- 페이지를 `header`–`main`–`section/article`–`footer` 구조로 구분
- H1은 페이지의 단일 주제, H2는 핵심 장, H3는 하위 질문에 사용
- 이동은 실제 `a[href]`, 동작은 `button`으로 구현
- 이미지에는 용도에 맞는 대체 텍스트를 제공하고 장식 이미지는 빈 `alt` 사용
- canonical, robots, sitemap, 리다이렉트와 상태 코드 정책을 함께 관리
- JavaScript 실행 전후의 DOM과 주요 콘텐츠 노출 여부 비교

### 검증 / 결과

- HTML validator와 접근성 검사로 구조 오류 확인
- 브라우저 JavaScript 비활성화 또는 렌더링 테스트로 핵심 콘텐츠 확인
- Search Console URL 검사·페이지 색인 보고서로 배포 결과 확인
- **검증 데이터가 없는 경우:** “구조 개선 적용”, “크롤링 점검 완료”처럼 작업 사실만 기록

## 2. Meta, OG, canonical

### 문제

모든 페이지가 같은 title과 description을 쓰거나 canonical이 실제 대표 URL과 다르면, 페이지의 주제와 공유 맥락이 흐려집니다.

### 전략

- title은 `페이지 고유 주제 — 브랜드` 순서로 작성합니다.
- description은 페이지가 누구에게 무엇을 제공하는지 한두 문장으로 설명합니다.
- canonical은 파라미터·프로토콜·슬래시 정책을 반영한 절대 URL을 사용합니다.
- OG 제목·설명·이미지는 검색 메타데이터와 메시지를 맞추되 채널 특성에 맞게 다듬습니다.

### 적용 예시

```html
<title>제품의 핵심 가치와 이용 방법 — 브랜드명</title>
<meta name="description" content="제품이 무엇인지, 왜 필요한지, 어떻게 이용하는지와 자주 묻는 질문을 확인하세요.">
<link rel="canonical" href="https://example.com/product/">
<meta property="og:type" content="website">
<meta property="og:title" content="제품의 핵심 가치와 이용 방법">
<meta property="og:description" content="What, Why, How와 FAQ로 정리한 제품 안내">
<meta property="og:url" content="https://example.com/product/">
```

### 검증 / 결과

배포된 HTML 소스, canonical 최종 도착 URL, 공유 디버거의 미리보기를 확인합니다. 제목 변경 뒤 노출·클릭 변화는 같은 기간의 Search Console 데이터가 있을 때만 성과로 연결합니다.

## 3. Structured data / Schema.org

### 문제

브랜드와 제품 정보가 화면에는 있지만 서로 어떤 관계인지, 운영 주체가 누구인지, 어느 정보가 공식 값인지 기계가 판단하기 어려울 수 있습니다.

### 전략

- 먼저 화면의 entity 정보를 명확하게 고친 뒤 JSON-LD를 추가합니다.
- 페이지 목적에 맞는 가장 구체적인 타입만 선택합니다.
- 보이지 않는 리뷰·가격·평점·FAQ를 스키마에만 넣지 않습니다.

### 적용

- 기업/브랜드 소개: `Organization`과 공식 URL·로고·동일 entity 링크
- 제품 상세: 실제 표시 정보와 일치하는 `Product` 속성
- 사이트 구조: `WebSite`, `BreadcrumbList`
- 질문 콘텐츠: 실제 화면에 같은 질문과 답이 있을 때만 `FAQPage` 검토
- 변경이 잦은 정보는 CMS/템플릿의 단일 데이터 소스에서 화면과 JSON-LD를 함께 생성

### 검증 / 결과

Schema Markup Validator와 Google Rich Results Test에서 문법·필수/권장 속성을 확인하고, 렌더링된 화면의 텍스트와 JSON-LD를 대조합니다. 유효한 스키마는 검색 기능 노출의 조건일 수 있지만 **노출 자체를 보장하지는 않습니다.**

## 4. 검색 의도 기반 콘텐츠와 FAQ

### 문제

브랜드가 하고 싶은 말의 순서와 사용자가 알고 싶은 순서가 다를 수 있습니다. 긴 캠페인 카피만으로는 “무엇인가”, “왜 필요한가”, “어떻게 이용하는가”에 빠르게 답하기 어렵습니다.

### 전략

- 대표 검색 의도를 정보 탐색, 비교, 이용 방법, 문제 해결 등으로 구분합니다.
- 한 section은 하나의 질문에 답하게 합니다.
- 첫 문장에 결론을 쓰고, 다음 문장에 조건과 근거를 보탭니다.
- FAQ는 검색량만 보고 만들지 않고 고객 문의·사이트 검색·현장 표현을 함께 반영합니다.

### 적용

```text
H1: 제품/서비스가 무엇인지
  H2: What — 무엇을 제공하는가
  H2: Why — 어떤 문제를 해결하는가
  H2: How — 어떻게 이용하는가
  H2: FAQ — 결정 전에 남는 질문
    H3: 질문 1
    H3: 질문 2
```

### 검증 / 결과

- 대표 질문을 처음 보는 사용자가 어느 section에서 답을 찾는지 확인
- 사이트 검색어·고객 문의·Search Console 질의를 다음 개편에 반영
- FAQ 답변의 정책·날짜·제품 정보가 최신인지 정기 확인

## 5. GEO / AEO 질문-답변 구조

### 문제

생성형 검색과 음성·답변형 검색은 긴 문장에서 제품의 정체, 대상, 차이, 사용법을 추출해 답을 조합합니다. 주어가 생략되거나 고유명사와 속성의 관계가 암묵적이면 잘못 요약될 가능성이 커집니다.

### 전략

- **질문 하나, 직접 답 하나:** 질문 heading 바로 다음 문장에 결론을 둡니다.
- **entity를 반복해 명시:** “이 제품”, “당사”만 쓰지 않고 정식 브랜드·제품명을 필요한 위치에 씁니다.
- **사실과 해석 분리:** 수치·정책·출처·기준일을 표시하고 홍보성 평가와 섞지 않습니다.
- **독립적으로 인용 가능한 단락:** 문단 하나만 떼어도 주체와 맥락이 남게 씁니다.

### 적용 템플릿

```markdown
### [제품명]은 무엇인가요?
[제품명]은 [대상]이 [핵심 문제]를 해결하도록 [핵심 기능/가치]를 제공하는 [카테고리]입니다.

### 왜 [제품명]을 사용하나요?
[구체적 상황]에서 [명시적 가치]가 필요하기 때문입니다. 적용 조건과 예외는 다음과 같습니다.

### 어떻게 이용하나요?
1. [첫 단계]
2. [둘째 단계]
3. [완료/확인]
```

### 검증 / 결과

- 브랜드명·제품명·핵심 속성을 묻는 고정 질문 세트를 만듭니다.
- 여러 검색/답변 환경에서 답의 정확성, entity 혼동, 공식 페이지 연결 여부를 관찰합니다.
- 결과는 날짜·질문·환경과 함께 기록하되, 통제되지 않은 한두 번의 노출을 성과 지표로 일반화하지 않습니다.

## 사례 후보

### Pure Gold — What / Why / How + FAQ

**상태: 정보 구조 경험을 정리한 사례 후보 · 검색 성과 미기재**

- **문제:** 제품 설명이 기능·캠페인 문구 위주로 흩어지면 사용자의 기본 질문과 제품 entity가 한눈에 연결되지 않을 수 있습니다.
- **전략:** `What → Why → How → FAQ` 순서로 제품 정의, 필요성, 이용/경험 방식, 남은 질문을 단계적으로 해소합니다.
- **적용:** 각 장을 질문에 대한 독립적인 답변 단위로 만들고, 제품명·카테고리·핵심 특성을 본문과 메타데이터에서 일관되게 표현하는 구조를 사용합니다.
- **검증 / 결과:** 구조 경험은 포트폴리오 사례로 정리할 수 있지만, 현재 문서에는 배포 URL·적용 전후 데이터·Search Console 근거가 연결되어 있지 않습니다. 따라서 순위·트래픽·전환 성과는 기재하지 않습니다.

추가 증빙이 확보되면 화면 캡처, 담당 범위, 실제 heading outline, 메타데이터/스키마 diff, 배포일과 검증 기록을 연결합니다.

### 한맥 — AEO 관점의 질문형 콘텐츠

**상태: 질문형 콘텐츠 경험을 재구성한 사례 후보 · 검색 성과 미기재**

- **문제:** 브랜드 콘텐츠가 감성 카피에만 의존하면 사용자의 구체적인 질문에 대한 직접 답과 브랜드/제품 정보의 관계가 약해질 수 있습니다.
- **전략:** 사용자의 표현을 질문 heading으로 만들고, 첫 문장에 직접 답한 뒤 상세 설명과 다음 행동을 연결합니다.
- **적용:** 질문별 독립 section, 결론 우선 답변, 명시적인 제품/브랜드명, 관련 페이지 내부 링크를 AEO/GEO 관점의 포트폴리오 구조로 정리합니다.
- **검증 / 결과:** 질문형 콘텐츠를 설계·운영한 경험 후보로 사용하되, 실제 적용 범위와 검색/답변 노출 효과는 배포 코드와 측정 자료가 확인되기 전까지 성과로 표현하지 않습니다.

### OB 기업 사이트 — 구조화 데이터

**상태: 기존 포트폴리오와 git 이력에 기록된 적용 경험 · 노출 성과 미기재**

- **문제:** 기업·뉴스룸·미디어 정보의 주체와 문서 성격을 검색엔진이 일관되게 해석할 구조가 필요했습니다.
- **전략:** 화면에 표시되는 기업/콘텐츠 정보를 기준으로 Schema.org 구조화 데이터를 연결합니다.
- **적용:** 영문 다국어 전환 작업과 함께 구조화 데이터를 적용한 경험이 기존 프로젝트 이력에 기록되어 있습니다.
- **검증 / 결과:** 구현 경험만 명시합니다. 리치 결과 노출, 검색 순위, 트래픽 개선 수치는 확인 자료가 없어 기재하지 않습니다.

## 적용 체크리스트

### 기획·콘텐츠

- [ ] 페이지의 대표 사용자와 대표 검색 의도를 한 문장으로 정의했는가
- [ ] H1이 페이지의 고유 주제를 설명하는가
- [ ] 각 H2/H3가 하나의 질문 또는 하위 주제에 답하는가
- [ ] 브랜드·제품·운영 주체·대상·핵심 속성을 명시했는가
- [ ] 핵심 답이 문단의 첫 문장에 있는가
- [ ] FAQ가 실제 질문을 사용하며 중복·추측 답변이 없는가
- [ ] 수치·정책·날짜에 출처와 기준일이 있는가

### 프론트엔드

- [ ] 핵심 콘텐츠와 내부 링크가 렌더링된 HTML에 존재하는가
- [ ] semantic landmark와 heading hierarchy가 논리적인가
- [ ] title·description·canonical이 URL별로 고유하고 일관적인가
- [ ] OG 정보와 공유 이미지가 실제 페이지 내용과 일치하는가
- [ ] 구조화 데이터가 화면의 정보와 일치하는가
- [ ] 모바일, 키보드, 스크린리더 환경에서 정보 순서가 유지되는가
- [ ] 404·리다이렉트·중복 URL·깨진 링크를 확인했는가

### 검증·운영

- [ ] HTML/Schema/Rich Results 검사 결과를 저장했는가
- [ ] 배포 전후 URL과 변경일을 기록했는가
- [ ] Search Console의 색인·검색 질의·클릭 데이터를 같은 조건으로 비교했는가
- [ ] GEO/AEO 대표 질문 세트와 점검 날짜를 기록했는가
- [ ] 검증되지 않은 상관관계를 성과로 단정하지 않았는가

## 성과 표기 규칙

| 표기 | 사용할 수 있는 조건 | 예시 |
|---|---|---|
| 적용 | 코드·배포 화면·작업 문서로 확인 가능 | “Organization JSON-LD를 적용했다” |
| 검증 | 검사 도구와 날짜가 기록됨 | “배포일 기준 Schema validator 오류 0건” |
| 변화 | 같은 기준의 전후 데이터가 있음 | “색인 제외 URL이 A에서 B로 변했다” |
| 성과 | 변화와 작업의 관계를 설명할 충분한 근거가 있음 | 기간·대상·측정 도구를 함께 명시 |
| 사례 후보 | 경험은 있으나 범위·결과 증빙이 부족함 | “AEO 관점으로 재구성 가능한 질문형 콘텐츠 경험” |

이 문서는 성과를 크게 보이게 만드는 문서가 아니라, **검색 경험을 어떤 기준으로 설계하고 무엇으로 증명할지를 보여주는 작업 기록**입니다.
